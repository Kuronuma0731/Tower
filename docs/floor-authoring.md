# 樓層授權流程 — 從主題到可玩的一層

樓層怎麼生出來的正式紀錄（2026-08-08 拷問定案）。格式定義見 [`data-schema.md`](data-schema.md)，每層引入什麼見 [`mechanics.md`](mechanics.md)。

## 已定決策

1. **內容等關卡編輯器**（維持原實作順序第 6 步）。編輯器因此成為**內容生產的關鍵路徑**——它的規格現在就定（見下），範圍收最小，目標是早落地，不是好用到可以上架。
   **唯一豁免（2026-08-08）**：F01 以工程測試層身分先行建造（`Core/Floors/F01.cs` + `data/floors/F01.json` 格式範本），供第 3 步最小可玩版；編輯器落地後匯入潤飾。F01 走了完整五步流程（預算表→佈局→驗證器），是其餘 9 層的流程示範。
2. **樓梯座標對齊**（傳統魔塔規約）：F(n) 的上樓梯與 F(n+1) 的下樓梯**同座標**——上樓後你就站在該層的下樓梯上。空間連續感、「逃回下層永遠一步之遙」、驗證器跨層模型單純，三者都靠這條。代價：每層佈局被樓梯座標鎖住一角。**匯入器與編輯器都要做配對檢查。**

## 生產管線（每一層都走完整五步）

```
① 主題       mechanics.md 逐層引入表——這層教什麼、考什麼
② 預算表     該層資源的數字分配（見下），人定方向、AI 算帳
③ 編輯器佈局  關卡編輯器（Godot `EditorPlugin`）內拉出地形與實體 → 輸出 floor JSON
④ 驗證器     可解性 + 守關合約 + 零傷檢查 + 樓梯配對，全過才算存在
⑤ 遊測       你在手機尺寸下實際走一遍——驗證器管「可解」，只有人管「好玩」
```

## ② 樓層資源預算表（佈局前必填）

封閉經濟（D11）下，佈局只是預算的空間化——先有數字才有地圖。每層一張：

| 欄位 | 說明 |
|---|---|
| 收入 | 本層投放：金幣掉落總和、經驗掉落總和、鑰匙 ×3 色、血瓶、寶石、沙漏 |
| 支出 | 本層需求：門 ×3 色、預期戰鬥損血、商店/祭壇的預期消費 |
| 淨流 | 收入 − 支出——**跨層資源曲線**由每層淨流串成，MVP 10 層的總曲線要先畫 |
| 緊繃度 | 淨流佔收入比。魔塔的靈魂：太鬆 = 無腦，太緊 = 卡死。目標帶開發期定 |

預算表以試算表維護（`data/floor-budget.csv`，欄位開工時定案），驗證器讀它核對「實際投放 = 預算宣告」。

## ③ 關卡編輯器 MVP 規格（僅此六項，多的不做）

1. 13×13 網格畫地形：`W . ^ v < >` 六種筆刷
2. 實體放置：從 `monsters.csv` / `items.csv` 下拉選 ref，點格子放置（門/樓梯/開關/商店/祭壇/NPC/spawn 同理）
3. **eid 自動生成**（`F08_m01` 格式），人手不可編輯
4. 輸出/讀回 `floors/*.json`（schema 版本 1）
5. 一鍵跑驗證器，結果面板顯示（不可解時列出缺口：差幾把鑰匙、差多少血）
6. 樓梯配對檢查（與上下層座標對齊）

明確**不做**：復原/重做、多層同時開、拖曳框選、美化預覽——那些是擴產期（25–30 層）才評估的。

## 佈局規範

- **密度**：內部 11×11 = 121 格，內容物（怪/門/道具/互動點）佔 **25–35%**，走道恆 ≥ 1 格寬
- **spawn**：全塔唯一一個 `spawn` 實體（1F），其餘樓層入場位置由樓梯對齊規約決定
- **單向字元語義**：`^v<>` 箭頭方向 = 通行方向（只能順著箭頭走）
- 每層做完 = 一個 git commit（字元列格式的 diff 就是關卡設計履歷）

## 與 mechanics.md 的分工

`mechanics.md` 管「這層引入什麼機制」（What），本文件管「怎麼把它做成一層」（How），預算表管「數字對不對」（How much）。三者衝突時，以 `CONTEXT.md` 的決策為準。
